# Keyboard handoff — updated 8 September 2026

## Decision

Sayso supports two deliberate flows. A finished result can be sent from Home or History and inserted with Full Access off. **Dictate in another app**, or the Keyboard Dictation Shortcut, starts capture in the foreground and permits returning to the destination app while that recording continues. Keyboard Stop/Discard requires Full Access; the Live Activity provides native system controls. Inserting text remains a separate explicit tap.

The app and both embedded extensions use public APIs and a common App Group. The keyboard never activates a microphone or launches Sayso. Ordinary microphone dictation retains its stop-on-background behavior. Simulator tests exercise the native Live Activity Stop intent and exact insertion into a real host field. Native iOS 27 simulator behavior is verified within the source boundaries below; physical background audio remains a separate gate.

## Verified public boundaries

| Operation | Evidence and consequence |
| --- | --- |
| Insert text into the active app | `UIInputViewController.textDocumentProxy` provides keyboard editing operations. Use `insertText`, `deleteBackward` and normal keyboard controls. A keyboard cannot arbitrarily reach another app’s view hierarchy. [Creating a custom keyboard](https://developer.apple.com/documentation/uikit/creating-a-custom-keyboard) |
| Read the app’s shared result | Apple explicitly permits read-only access to the containing app’s shared containers when Full Access is off. Both targets still need the same App Group entitlement. [Open access configuration](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard) |
| Write keyboard commands | Shared-container writes require `RequestsOpenAccess = true` and the person enabling Allow Full Access. Read-only insertion does not. Full Access does not grant microphone access. [Open access configuration](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard) |
| Launch Sayso from the keyboard | Do not promise this. `NSExtensionContext.open` is extension-point-dependent; its documentation names Today and iMessage support, not keyboard support. App Review 4.4.1 says keyboards must not launch apps other than Settings. [NSExtensionContext.open](https://developer.apple.com/documentation/foundation/nsextensioncontext/open(_:completionhandler:)), [App Review 4.4.1](https://developer.apple.com/app-store/review/guidelines/#extensions) |
| `Button(intent:)` in a keyboard | The SwiftUI initializer is public, but its documentation provides no keyboard-specific activation permission. An API compiling is not proof that it can foreground the containing app from this extension point or override the keyboard rule. No affirmative Apple documentation or Apple-staff answer establishing that exception was found. [Button initializer](https://developer.apple.com/documentation/swiftui/button/init(intent:label:)) |
| Open through a system Shortcut | An AppIntent with `.foreground(.immediate)` requests that the app be foregrounded before its action runs. Use this supported system surface, then wait for Sayso’s active scene before audio activation. [Intent supported modes](https://developer.apple.com/documentation/appintents/appintent/supportedmodes-5zhmb) |
| Automatically return to an arbitrary host app | No supported route was established. Do not inspect private host IDs, walk responder chains, call private LaunchServices, or hardcode URL schemes pretending to identify the originating app. The initial UX requires a manual switch. |

Keyboard availability also depends on the target field and app: secure fields and certain phone-pad fields substitute the system keyboard, and apps can decline custom keyboards. Therefore “works in every app/field” is not an accurate claim. [Apple’s custom keyboard guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html)

## Finished-text handoff contract

1. The person records or imports in Sayso, reviews/edits, then explicitly selects **Send to keyboard**. Sharing is independent of saving history. No history list, raw audio or surrounding host-field text enters the shared container.
2. The app atomically publishes `id`, exact `text`, `createdAt` and `expiresAt` to `group.solimanali.Sayso`. A handoff expires after ten minutes; a new publication replaces the previous one. File protection applies while locked. A missing entitlement/container is an actionable failure, never a fallback to a guessed directory.
3. The person switches back, focuses the destination and selects Sayso with the globe. The keyboard reads the current handoff and shows a short preview and **Insert**.
4. Insert re-reads and validates the handoff, checks it still matches the displayed ID/text, then calls the active `textDocumentProxy.insertText`. It marks that handoff consumed only in its own sandbox to suppress accidental repeated taps. There is no automatic insertion on keyboard appearance.
5. The next-keyboard globe, typed characters and editing keys work with no handoff and no Full Access. The keyboard never reads the clipboard, collects surrounding field context or launches the app.

The read-only keyboard cannot delete the shared payload or acknowledge consumption to the app. Expiration hides it from the keyboard; it does not claim that the OS deletes the bytes at that instant. The containing app replaces or clears its own file. Insertion has no transactional acknowledgment from the host field, so do not claim exactly-once delivery across arbitrary host crashes. Keep the reviewed result available in Sayso for recovery.

## Explicit ongoing recording

Apple permits an already active recording session to continue in the background using the `audio` background mode and an appropriate `AVAudioSession` category. Normal recording activation from a background state is privacy-blocked; an Apple DTS engineer explicitly distinguishes special communication frameworks, which are not appropriate substitutes for a dictation app. [Recording category](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/record), [Apple DTS explanation](https://developer.apple.com/forums/thread/816408)

Implemented flow: a foreground Shortcut or in-app action starts Sayso → foreground permission/assets/preparation → recording and a Live Activity start → the person returns to their app → keyboard or Live Activity submits an ID-scoped Stop/Discard → Sayso stops capture, finishes transcription, optionally rewrites, and shares the result → the person taps Insert.

The microphone service checks foreground state immediately before audio-session activation and engine start. ActivityKit must be enabled; inability to create visible system UI cancels capture. The recording limit is ten minutes measured with a monotonic clock. There is no silent warm session between recordings and no microphone activation from an extension or a background intent.

Only session metadata and commands use protection until first unlock. Audio/transcript content never appears in the Live Activity. The shared result keeps complete file protection. A fifteen-second heartbeat lease hides abandoned sessions; polling runs only during the active session and its finite completion interval. NSFileCoordinator serializes writers across app/extension processes. New commands require a live matching session; an already-accepted Discard remains terminal for that UUID even when the app is delayed. An old session cannot overwrite or clean up a new one.

ActivityKit status is refreshed every five seconds with a fifteen-second freshness window. The native timer is capped at the last confirmation plus that window; stale UI offers **Open Sayso** and hides recording controls. An observed stale, dismissed, or disabled activity asks the app to finish capture or preserve its current source. On launch the coordinator snapshots and ends activities left by a previous process before creating a new one. This handles an activity outliving its app, but system delivery and display timing remain device checks. [Apple: displaying live data](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities), [stale dates](https://developer.apple.com/documentation/activitykit/activitycontent/staledate)

Completion checks pending Discard and publishes the final result inside the same coordinated transaction. Cancellation before that commit removes the active session’s provisional history and shares nothing. Cancellation after commit cannot hide the already-shared result. Ordinary private-history settings still apply independently of the deliberately chosen keyboard destination.

After capture stops, writing has at most sixty seconds and the system may grant less background time. Both deadlines keep the latest captured source and cancel unfinished model work. Refinement uses a committed full original; expiration during speech finalization refreshes a prior checkpoint with the latest captured words. Cancellation stops polling synchronously, so a late deadline cannot republish a discarded recording.

Native `LiveActivityIntent` Stop/Cancel runs in the containing app’s process and submits the same mailbox command. It never starts audio. Lock Screen interactions execute after the person authenticates; the metadata’s file-protection class does not bypass authentication. [Apple: adding interactivity to widgets and Live Activities](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities)

`AudioRecordingIntent` is relevant to future system recording controls but is not a keyboard-launch exemption. Apple requires an active Live Activity for its recording lifetime; without one, recording stops. Its presence in the SDK does not remove the foreground activation boundary. [AudioRecordingIntent](https://developer.apple.com/documentation/appintents/audiorecordingintent)

Apple lists **Xcode 27 beta 6, build 27A5252f**, released August 24, 2026. It contains the iOS 27 SDK and requires Apple silicon and macOS Tahoe 26.4 or later. Apple’s releases page separately lists iOS 27 beta 8 (24A5430a), August 31; Xcode and OS beta numbers differ. [Official release](https://developer.apple.com/news/releases/?id=08102026g), [system requirements](https://developer.apple.com/xcode/system-requirements), [release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes), [OS releases](https://developer.apple.com/news/releases/)

At this earlier feasibility check, the Mac was arm64, macOS 26.6.2, with Xcode 26.6 (17F113), iOS 26.5 SDK/runtime, and approximately **6.48 GiB** free at the check. Its existing Xcode occupies approximately 4.0 GiB on disk. The host OS meets the published Xcode 27 requirement. The official Applications download link redirects to Apple-account sign-in, so the exact archive/build download size and iOS 27 simulator size were not verified. There is insufficient evidence to promise that archive + extraction + runtime + build headroom fits. No download, installation, account mutation or cleanup was performed. Preserve the working installation; obtain adequate free space or an approved external destination, verify the authenticated sizes, then install side-by-side and run iOS 27 checks before claiming support. [Official download entry](https://developer.apple.com/download/)

An additional read-only check found `/Volumes/Untitled`, an ExFAT USB volume with **95,894,372,352 bytes free (about 89.3 GiB)**. At that time internal free space had fallen to about 5.1 GiB during builds/tests. The external filesystem advertises writability; Foundation reports no extended-security or sparse-file support. This metadata does not establish macOS privacy permission for Codex to write there. A suitable candidate is a new APFS sparsebundle disk image stored on this volume, keeping the existing files and format intact, then storing the Xcode archive, expanded application and DerivedData on the mounted APFS volume. This is an engineering recommendation based on the observed filesystem and Apple's documented image formats, not a tested Xcode installation. Prefer a sparsebundle over assuming efficient sparse-file behavior on ExFAT. [Apple: create an APFS disk image](https://support.apple.com/guide/disk-utility/create-a-disk-image-dskutl11888/mac)

Apple documents `xcodebuild -downloadPlatform … -exportPath …` for runtime exports and importing the resulting bundle. Exporting to external storage does not establish that installation, device data and caches all stay external; those internal-space requirements still need measurement before proceeding. No external directories/images were created and no files on that volume were inspected or changed. [Additional Xcode components](https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components)

A later attempt to preserve generated Sayso verification evidence on that volume triggered macOS `kTCCServiceSystemPolicyRemovableVolumes` permission prompting. The attempt was stopped before its destination directory existed; no files were copied, moved or deleted externally. That OS permission is a further prerequisite for external installation/storage. Local disk pressure was relieved by removing 555 MB of duplicate exported test attachments; every original `.xcresult` bundle and published screenshot was retained.
